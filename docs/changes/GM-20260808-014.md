# GM-20260808-014：Operation 执行元数据与错误契约

日期：2026-08-08

## 变更范围

本轮把设计文档已经要求、但开发垂直切片尚未公开的 Operation 执行元数据贯通到 Go 领域模型、development-memory Store、OpenAPI、前端类型、Mock 与界面。目标是让客户端能够区分排队、执行检查点和安全失败原因，同时继续明确这不是生产级任务租约或分布式 Worker。

## 已实现

- `domain.Operation` 新增 `attempt`、`maxAttempts`、`leaseOwner`、`leaseExpiresAt`、`checkpoint` 和结构化 `error`；统一构造器保证新 operation 从 `queued`、`0%`、`1/1` 和 `checkpoint: queued` 开始。
- development-memory Store 的 provision、电源、备份创建、恢复、备份删除和 reconcile 路径统一进入 running 与终态辅助函数。运行阶段写入固定开发 worker lease 和按类型细分的 checkpoint；成功与失败终态均清除 lease。
- provision、电源、备份创建、恢复和 reconcile 在提交结果前发现目标服务器不存在或 generation 不匹配时，使用 `{ code: "OPERATION_STALE", retryable: false }`，避免资源未应用但 operation 假成功；恢复摘要在执行期间失效时使用 `BACKUP_INTEGRITY_FAILED`。公开错误 message 不包含宿主路径、命令、凭据或其它内部实现信息。
- OpenAPI 3.1 将新增字段设为 Operation 的必需字段；可空的 lease 和 error 显式返回 `null`。`OperationError` 使用 closed object，固定包含 `code`、`message` 与 `retryable`。
- Web 手写类型、生成类型、Mock 和测试数据已同步。Mock 使用统一 queued/completed 构造器；活动操作展示 checkpoint 与尝试次数，失败提示优先使用 API 提供的安全结构化错误 message。创建服务器和电源操作把 accepted 作为 warning，并等待终态后才显示成功；Provision 失败时不会无条件跳转详情。
- `04-domain-model.md`、`08-api-contracts.md` 与 `11-testing-roadmap.md` 已同步当前能力和生产缺口。

## TDD 与 mutation 证据

- Go 回归测试先因 `Operation` 缺少新增字段而编译失败，随后验证 queued、running、succeeded 与 failed 生命周期的字段不变量。
- provision、电源、备份创建和 reconcile 的 stale generation 回归先观察到 `succeeded/completed` 假终态，备份路径还会错误创建恢复点；generation-aware 终态转换修复后，4 条路径均返回 `failed`、清除 lease，并携带不可重试的 `OPERATION_STALE`。已有 stale restore 回归继续验证同一错误语义且不破坏恢复点。
- 临时把成功终态 checkpoint 改回 `queued` 后，生命周期回归测试按预期失败；恢复实现后重新转绿。
- 前端新增结构化错误 message 的优先级测试，以及电源/Provision 的 accepted 与终态消费测试；对应 mutation 分别验证忽略错误 message、失败后仍跳转会被回归捕获。TypeScript 编译器约束所有 Operation literal 必须提供新增字段。
- HTTP 原始 JSON 回归验证 queued operation 始终包含执行元数据，并把空的 `leaseOwner`、`leaseExpiresAt` 和 `error` 显式编码为 `null`；临时为 `error` 加上 `omitempty` 后测试按预期失败，恢复后重新转绿。
